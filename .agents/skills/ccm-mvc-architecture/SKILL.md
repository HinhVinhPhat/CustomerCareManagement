# ASP.NET Core MVC architecture (WebBanSach sample)

A single MVC project under `src/`, with the same folder split as the WebBanSach project. No
separate API, no separate BLL/DAL projects. Read `ccm-database` first: the database already holds
the business logic, and the Services layer only **calls into** it.

## Structure

```
src/CcmWeb/
  Controllers/        thin controllers: receive the request, call a Service, return a View/Redirect
  Helpers/
    Utils.cs          helpers (money/date formatting, reading claims, translating SQL errors...)
    WorkConstants.cs  constants: roles, statuses, types, tiers... matching the DB CHECK constraints
  Models/
    EF/ApplicationDbContext.cs        generated by the scaffold, DO NOT hand-edit
    EF/ApplicationDbContext.Custom.cs extra configuration (partial), edit here
    Entities/         entities generated by the scaffold (tables and views), DO NOT hand-edit
    ViewModels/       models for forms, lists, dashboard (added on top of WebBanSach)
    ErrorViewModel.cs
  Services/
    ICustomerService.cs   CustomerService.cs     (interface + class pair, like IBookServices/BookServices)
  Resources/
    SharedResource.resx      every visible string, Vietnamese (the neutral/default language)
    SharedResource.en.resx   the English text of the same keys
  SharedResource.cs     empty marker type for IStringLocalizer<SharedResource>
  Views/              Razor, Views/Shared/_Layout.cshtml
  wwwroot/            css, js, images
  Program.cs
tests/CcmWeb.Tests/   xUnit (see the ccm-workflow skill)
```

URLs follow the sitemap in `docs/design.md` section 4 (for example `/customers`,
`/contracts/create`, `/login`): use attribute routing (`[Route("customers")]`) instead of the
default `/Customer` route.

Naming convention: PascalCase English domain names (`Customer`, `Contract`, `Feedback`, `Care`,
`Contact`, `Report`, `Account`). One controller and one `I<Ten>Services` / `<Ten>Services` pair
per business area. DI registration: `AddScoped<ICustomerService, CustomerService>()`.

Do not add: generic repository, UnitOfWork, empty interfaces, scaffolding for modules that are
not built yet, or libraries outside the approved list (Dapper, AutoMapper, MediatR...) without
approval.

## Entity Framework Core: database-first only

The schema is owned by `database/*.sql`. **No migrations, no `EnsureCreated`.** Generate the
model from the running DB (run inside the project folder; needs the `dotnet-ef` tool and the
`Microsoft.EntityFrameworkCore.Design` package):

```bash
dotnet ef dbcontext scaffold "Name=ConnectionStrings:DefaultConnection" Microsoft.EntityFrameworkCore.SqlServer \
  --context ApplicationDbContext --context-dir Models/EF --output-dir Models/Entities --no-onconfiguring --force
```

After a schema change, run the 4 SQL files again and re-scaffold (`--force` overwrites). Because
of that, **every customisation must live outside the scaffolded files**: use
`partial void OnModelCreatingPartial(ModelBuilder)` in `ApplicationDbContext.Custom.cs` and
partial classes for entities. EF Core 8 or later is required (for `SqlQueryRaw` with arbitrary
types and `UseSqlOutputClause`).

Data types: DATE columns become `DateOnly`, DATETIME becomes `DateTime`, money is `decimal`. DATE
fields in ViewModels/forms also use `DateOnly` so no time part sneaks in.

## The big trap: tables with triggers and EF Core

EF Core writes `INSERT`/`UPDATE` with an `OUTPUT` clause by default. SQL Server does **not allow**
`OUTPUT` (without `INTO`) on a table that has triggers, and reports error 334 on `SaveChanges`.
This database has triggers on `CONTRACT`, `CONTRACT_DETAIL`, `CUSTOMER`, `FEEDBACK`. Declare it in
`OnModelCreatingPartial` (sample in `references/code-mau.md`) for each of those entities, then
**actually try it once** (add a feedback row through EF); if error 334 persists the configuration
is incomplete.

Columns owned by a trigger/DB (`TotalValue`, `Tier`, `ResolvedDate`, `AUDIT_LOG`) must not be
written from the application. The safe write paths:

| Task | How |
|---|---|
| Contract: add, sign, renew, cancel | Call the procedure (`ExecuteSqlRawAsync` with `EXEC dbo.sp_...`). Do not use EF to insert/update `CONTRACT`, `CONTRACT_DETAIL` |
| Customer: add | EF `Add` (do not set `Tier`; let the DB use its default) |
| Customer: edit | `ExecuteUpdateAsync` listing only the editable columns (name, email, phone, address, source, owner...), never touching `Tier` |
| Customer: deactivate / reactivate | `sp_SetCustomerStatus` |
| Contact, care | EF `Add` (optionally `Update`), with `EmployeeID` from the logged-in user |
| Feedback: receive | EF `Add` (EmployeeID null, status "New") |
| Feedback: assign, change status | `sp_AssignFeedback`, `sp_UpdateFeedbackStatus` |
| Reading lists, dashboard, reports | A view (keyless entity generated by the scaffold) or `Database.SqlQueryRaw<T>("EXEC dbo.sp_...")` |

Reading data for display uses `AsNoTracking()`.

## Mandatory: SESSION_CONTEXT for the audit log

The audit triggers read the actor from `SESSION_CONTEXT('EmployeeID')`. Use a
`DbConnectionInterceptor` that runs `EXEC sp_set_session_context N'EmployeeID', @employeeID`
every time EF opens a connection, with `employeeID` read from the logged-in user's claim
(`IHttpContextAccessor`). Sample in `references/code-mau.md`. If you open a connection yourself
with `Database.GetDbConnection()`, you must open it through `Database.OpenConnectionAsync()` so
the interceptor runs. Background work (no user) has no `EmployeeID` and the log records NULL,
which is correct.

Check: after acting on a contract or feedback through the UI,
`SELECT TOP 5 * FROM AUDIT_LOG ORDER BY LogID DESC` must show the logged-in user's `EmployeeID`.

## Layering

- **Controller:** no SQL, no business rules. Check permission with `[Authorize(Roles = ...)]`
  (see `ccm-auth-security`), check `ModelState`, call a Service, return a View or
  `RedirectToAction` with `TempData` (the message key the layout turns into a toast or an alert).
- **Service:** holds the `ApplicationDbContext`, calls procedures/views, normalises input data,
  translates SQL errors. Returns ViewModels/DTOs or lists, **never `IQueryable`** or tracked
  entities to the controller.
- **View:** display only, no business logic, no DB access.
- The acting `employeeID` comes from the claim (a helper in `Helpers/Utils.cs`), never from the form.
- Business errors: the Service throws `BusinessException` with an English message; the controller
  catches it and shows it with `ModelState.AddModelError(string.Empty, ...)` or `TempData`. Never
  let a raw SQL error reach the user.

## Translating SQL errors

The error code is in `SqlException.Number`, possibly inside `InnerException` (EF wraps it in
`DbUpdateException`). Full code table in `ccm-database/references/schema.md`. One function in
`Helpers/Utils.cs` (`TranslateSqlError` / `TranslateSqlNumber`, sample in `references/code-mau.md`)
shared by all Services returns a **resource key**, never a finished sentence:

- 50001-50015: map the code to its key (`Error_FeedbackNeedsAssignee`, `Error_ContractNotFound`...).
  The English `THROW` text is for the log, not for the user.
- 547: read the constraint name from the message (`CHK_Feedback_Assignee`, `CHK_Customer_Business`,
  `CHK_Care_SatisfactionScore`, `CHK_Settings_Value`, `FK_...`/`REFERENCE`) and return that key.
- 2601 and 2627: read the index name (`UX_Customer_Email`, `UX_Employee_DepartmentManager`,
  `UQ_Settings_Scope`...).
- Anything else: return `null`, so the caller logs the exception, shows the generic
  `Error_Unexpected` in the user's language, and never exposes SQL details.

`BusinessException` carries `MessageKey` plus optional arguments - the view renders `@L[key]` in the
language the user is reading. Never build the sentence inside the Service.

## Localization and display settings

- Vietnamese is the default language and English is the second one; the split between code and screen
  text is in the `ccm-language` skill. Every visible string is a key in
  `Resources/SharedResource*.resx`, both files always in step.
- `Program.cs`: `AddLocalization(options => options.ResourcesPath = "Resources")`,
  `AddControllersWithViews().AddDataAnnotationsLocalization(...)` pointing at `SharedResource` (so the
  `ErrorMessage` and `Display(Name = ...)` values in a view model are KEYS, not sentences),
  `Configure<RequestLocalizationOptions>` with the providers in the order query string -> cookie ->
  system default from the database -> `Accept-Language`, and `app.UseRequestLocalization()` after
  `UseStaticFiles()`.
- Register `HtmlEncoder.Create(UnicodeRanges.All)`. Without it Razor sends every Vietnamese letter as a
  numeric entity (`&#x110;&#x103;...`); with it the letters travel as UTF-8 while `&`, `<`, `>`, `"`
  and `'` stay escaped, so user data is still safe.
- Views take the localizer once: `@inject IStringLocalizer<SharedResource> L` in
  `Views/_ViewImports.cshtml`, then `@L["Key"]` for text and `@L.Label("Role", role)` /
  `@L.Label("Setting", key)` for coded values. Coded values (roles, statuses, themes, languages) stay
  English in the database and in the code; only their labels are translated.
- Display preferences (`SETTINGS`: `Language`, `Theme`) are read through `vw_SystemSettings` and
  `vw_EffectiveSettings`, so the "a personal row beats the system default" rule lives in SQL and is
  never re-implemented in C#. `SettingsService` is scoped and caches its reads for the request; a cookie
  answers first, so the layout normally costs no query at all.
- A display preference must never stop a page from rendering: when the database cannot answer,
  `SettingsService` logs the failure and the hard-coded defaults (`WorkConstants.DefaultLanguage`,
  `DefaultTheme`) apply.
- The language cookie is the framework's own (`.AspNetCore.Culture`, written with
  `CookieRequestCultureProvider.MakeCookieValue`); the theme cookie (`.CcmWeb.Theme`) is plain and not
  `HttpOnly`, because it holds no secret. Right after a successful sign-in the two cookies are filled
  from `vw_EffectiveSettings`, so the account's own choice applies on the first page.


## Configuration

- Connection string named `DefaultConnection`, using the login `app_ccm` (never `sa`). Dev: User
  Secrets (`dotnet user-secrets set "ConnectionStrings:DefaultConnection" "..."`). Docker:
  `ConnectionStrings__DefaultConnection` environment variable. Never put real values in
  `appsettings.json` and never commit them.
- `TrustServerCertificate=True` is needed in dev against a SQL Server with a self-signed certificate.
- Background work: `sp_ExpireContracts` runs at start-up and once a day from a `BackgroundService`
  (the container has no SQL Agent). Sample in `references/code-mau.md`.
- The lists of valid values (roles, statuses, types...) live in `Helpers/WorkConstants.cs`, shared
  by validation and dropdowns.
- List paging: `Skip/Take` on the view query, or in-memory paging when a procedure returns the whole set.

## Check after every feature

1. Clean build, runs against the sample data.
2. Writes go through a procedure (contracts, feedback) or the correct write path in the table
   above; no `TotalValue` or `Tier` written from the application.
3. `AUDIT_LOG` has the correct `EmployeeID`.
4. Trigger a business error (renew a cancelled contract) and see the message in the user's language,
   with no SQL text and no constraint name in it.
5. The right role can reach the page and a wrong role is redirected to the access-denied page.
6. The page is read in both languages (`VI`/`EN` switch) and in both themes, and no string is typed
   straight into the `.cshtml`.
